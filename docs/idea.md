# MediON — 기획서 (idea.md)

> 의사를 찾아 예약하고, 비대면으로 진료받고, 결제 후 처방전을 받아 가까운 약국에서 약을 받는 **비대면진료 앱**
> **포트폴리오용 데모 프로젝트입니다. 실제 서비스로 배포하지 않으며, 모든 사용자·의사·약·진료 데이터는 가상입니다.**

기능 목록과 완료 기준은 [requirements.md](./requirements.md), 구현 설계는 [tech-spec.md](./tech-spec.md) 참고.

---

## 1. 한 줄 소개

증상에 맞는 의사를 골라 원하는 시간에 예약하고, 진료 → 결제 → 처방전 → 약국 선택 → 약 수령까지 **한 앱에서 이어지는** 비대면진료 서비스. 직접 기획한 **질문·답변(Q&A)**은 진료로 들어가는 입구 역할을 하는 부가 기능입니다.

## 2. 배경

### 출발점
- 기존 비대면진료 앱을 Figma로 리디자인하면서 **질문 글 작성 + 의사 답변** 기능을 직접 추가로 기획함
- 처음에는 범위가 작은 Q&A만 떼어 독립 앱으로 만들려고 했음
- 하지만 포트폴리오로 보여줄 핵심은 결국 **비대면진료 흐름 자체**라고 판단해서 방향을 바꿈 (11. 결정 기록)

### 해결하려는 문제
| 문제 | 이 앱의 해결 방식 |
|---|---|
| 어느 진료과로 가야 할지 모르겠음 | 증상 카테고리(감기, 두통, 피부 등)로 고르면 맞는 진료과 의사 목록 |
| 병원 갈 시간이 없음 | 원하는 시간에 예약하고 비대면으로 진료 |
| 진료 후 처방전·약국·결제가 따로 놀아 번거로움 | 예약 상세 하나에서 진료 → 결제 → 처방전 → 약 수령까지 진행 단계로 확인 |
| 진료까지 받을 일인지 판단이 어려움 | (2차) 먼저 질문하고 의사 답변을 본 뒤, 필요하면 그 의사에게 바로 예약 |

## 3. 핵심 가치

1. **끊기지 않는 흐름**: 예약부터 약 수령까지 한 화면(예약 상세)의 진행 단계로 이어짐
2. **믿을 수 있는 의사**: 면허 서류 제출 → 관리자 승인을 거친 의사만 진료
3. **실제와 같은 처리 방식**: 중복 예약 방지, 서버 금액 검증을 거친 결제 승인, 진료 완료와 처방·결제 요청을 한 번에 처리
4. **제도를 고려한 설계**: 초진 처방 일수 제한, 약 배송 대상자 제한 등 실제 제도를 화면과 규칙에 반영

## 4. 사용자와 페르소나 (가상)

| 역할 | 설명 |
|---|---|
| 게스트 | 로그인 없이 의사 목록·상세를 둘러봄. 예약하려면 로그인 |
| 환자 | 이메일로 가입. 본인 또는 가족을 위해 예약·진료·결제 |
| 의사 | 면허 서류를 제출하고 관리자 승인을 받아야 진료 가능 |
| 관리자 | 의사 인증 심사 (시드 계정만) |

| 페르소나 | 상황 | 이 앱에서 하는 일 |
|---|---|---|
| **환자 A** · 30대 직장인 | 감기 기운이 있는데 병원 갈 시간이 없음 | 증상 카테고리 → 오늘 가능한 의사 예약 → 진료 → 결제 → 회사 근처 약국에서 약 수령 |
| **보호자 B** · 60대 부모님을 챙기는 30대 자녀 | 부모님 대신 예약하고 진료 내역을 같이 보고 싶음 | 가족 등록 → 부모님을 진료받는 사람으로 예약 (진료비는 부모님 나이 기준) |
| **의사 C** · 개원 3년 차 정형외과 전문의 | 진료 시간 중 비는 시간에 비대면 진료를 보고 싶음 | 진료 일정 확인 → 진료 시작·완료 → 처방전 작성 |

> 페르소나는 시드 데이터 계정으로 만들고, 시연용 로그인 정보는 README에만 적습니다. 앱 화면에는 "체험하기" 같은 데모 전용 진입점을 두지 않습니다.

## 5. 핵심 사용자 흐름 (1차)

```
[환자] 증상 카테고리 선택 → 의사 목록 → 의사 상세 (진료 시간표, 진료비, 후기)
   ↓
[환자] 날짜·시간 선택 → 진료받을 사람(본인/가족) → 증상 메모 → 예약
   ↓
[의사] 진료 일정에서 예약 확인 → 진료 시작 → 진료 완료 (진료 요약 + 처방전 작성)
   ↓                                    └ 화상통화는 보류, 상태 변경만
[환자] 결제 요청 알림 → 토스 테스트 결제 → 서버 승인
   ↓
[환자] 처방전 열람 ("데모 처방전") → 근처 약국 선택 → 처방전 전송
   ↓                                    └ 기본 방문 수령, 대상자만 배송
[환자] 조제 중 → 수령 대기 / 배송 중 → 수령 완료 ("데모: 다음 단계로" 버튼)
   ↓
[환자] 진료 후기 (재진 희망, 태그)
```

### 2차: 질문·답변과 진료 연결

처음 Figma 초안의 "최근 작성한 글이 있으신가요?"(예약할 때 내 질문 불러오기)를 살립니다.

```
질문 작성 → 의사 답변 → "이 의사에게 비대면 진료 받기" → 예약 화면 (질문 내용이 증상 메모로 자동 첨부)
                     └ 의사가 "대면 진료 권유" → 추천 진료과의 근처 병원 찾기
```

## 6. 기능별 구현 수준

데모라서 실제로 할 수 없는 부분은 **흐름과 상태는 진짜로 만들고, 외부 연결만 데모로 대신**합니다.

| 기능 | 구현 수준 | 방식 |
|---|---|---|
| 의사 찾기 | ✅ 실제 구현 | 증상 카테고리 → 진료과 매핑, 오늘 가능 여부·다음 가능 시간, 재진 희망률 |
| 예약 | ✅ 실제 구현 | 의사별 진료 시간표, 30분 단위, 가족 예약, 초진·재진 판정. **같은 시간 중복 예약을 DB 제약으로 방지** |
| 진료 | ⚠️ 상태만 | 의사가 진료 시작 → 진료 완료로 상태를 바꿈. 화상통화는 보류 (12. 참고) |
| 처방전 | ✅ 실제 구현 (데모 데이터) | 의사가 시드 약 목록에서 검색해 작성. 환자는 결제 후 열람, "데모 처방전" 워터마크 |
| 결제 | ✅ 테스트 결제 | 토스페이먼츠 테스트 키 (실제 돈 안 나감). 결제창 → 서버 승인, **서버에 저장된 금액으로 검증** |
| 약국 선택 | ✅ 실제 구현 | 공공데이터 약국 정보 + 카카오맵. 처방전 전송은 앱 안에서만 기록 (실제 약국에 전송 안 됨) |
| 약 수령·배송 | ⚠️ 상태 흐름만 | 약국 쪽 화면이 없으므로 "데모: 다음 단계로" 버튼으로 상태 진행 |
| 알림 | ✅ 실제 구현 | 예약·취소·결제 요청·약 상태 알림, 30초 주기 조회 |
| 후기 | ✅ 실제 구현 | 재진 희망, 태그, 의사 상세에 통계 |
| 질문·답변 | ✅ 2차 | 이미 설계·목업 완료. 질문 → 예약 연결 |
| 근처 병원 찾기 | ✅ 2차 | 심평원 병원정보 + 카카오맵 |

## 7. 제도와 규제 고려 (2026-10 기준, 참고용)

### 비대면진료 제도화
- 비대면진료 제도는 **2026-12-24 시행** 예정
- 초진 처방은 **최대 7일**로 제한하는 방향으로 보도됨 → 처방전 작성 시 초진이면 투약 일수 7일까지만 입력 (L-2). 세부 기준이 확정되면 다시 확인
- 약 배송은 **섬·벽지 거주자, 장기요양 수급자, 장애인, 희귀질환자**에게 우선 허용하는 쪽으로 초기 합의, 대상 확대는 논의 중 → **기본 = 약국 방문 수령, 대상자만 = 배송 옵션** (M-2)

### 플랫폼 관련
- 플랫폼의 의약품 도매업을 막는 약사법 개정 (2026-09 공포, 2027-09 시행) → 앱은 약을 직접 팔거나 유통하지 않고 **약국 선택과 처방전 전달만** 담당
- 환자를 특정 병원·약국으로 보내고 건당 수수료를 받는 구조는 의료법상 환자 유인·알선 소지 → 수익 모델에서 제외 (8. 참고)
- 약국 목록은 거리순으로만 정렬하고 특정 약국을 앞에 두지 않음

> 위 내용은 포트폴리오 기획을 위한 일반적인 검토이며, 실제 서비스라면 법률 전문가 검토가 필요합니다.

## 8. 비즈니스 모델 (설계안 · 3차)

데모에서는 구현하지 않고, 실제 서비스라면 어떻게 할지 설계만 해둡니다 (requirements.md X 영역).

| 대상 | 무료 | 유료 (설계안) |
|---|---|---|
| 환자 | 의사 찾기, 예약, 진료 (진료비는 의료기관에 지불) | 없음 |
| 의사 | 진료, 처방전 작성 | **파트너 플랜**(월 정액, X-1): 프로필 강화, 진료 통계, 진료 시간표 관리 도구 |

설계 원칙
- 진료 건당·약국 연결 건당 수수료를 받지 않음 (알선 소지)
- 파트너 플랜 의사도 **검색 순위는 동일**, 보이는 정보량만 다르게
- 의사 답변(2차)에는 과금하지 않음

## 9. 범위와 단계

| 단계 | 내용 | 목표 |
|---|---|---|
| **1차** | 인증·의사 인증 → 의사 찾기 → 예약 → 진료(상태) → 결제 → 처방전 → 약국 → 후기, 알림 | 이것만으로 "비대면진료 앱을 처음부터 끝까지 만들었다"고 설명할 수 있게 |
| **2차** | 질문·답변, 질문 → 예약 연결, 근처 병원 찾기 | 직접 기획한 기능 추가 |
| **3차** | 화상통화(보류 해제 시), 실시간 알림(SSE), 파트너 플랜 | 고도화 |

자세한 개발 순서는 requirements.md 6. 개발 순서 참고.

### 비목표 (만들지 않는 것)
- 실제 서비스 배포, 실사용자 모집
- 실제 결제 (토스페이먼츠 테스트 결제만)
- 실제 약국 연동·실제 약 배송 (상태 흐름만 데모)
- 면허 진위 자동 확인 (공개 API가 없어 서류 제출 + 관리자 수동 승인까지만)
- 실제 진단·처방 (처방전은 시드 약 목록으로 만든 데모 데이터)
- AI가 생성하는 의료 답변
- 치과·한방 진료 (의사 면허와 다른 면허 체계라 1차에서 제외)

## 10. 기술 스택

풀스택 역량을 보여주기 위해 **인증·권한·예약·결제 승인 로직을 직접 구현**하는 구조입니다.

| 영역 | 선택 | 이유 |
|---|---|---|
| 프론트엔드 | React + Vite + React Router (JavaScript), Tailwind CSS v4, TanStack Query | 익숙한 스택, 상태별 UI를 빠르게 구성 |
| 백엔드 | FastAPI (Python) | 인증·권한·상태 변경·트랜잭션을 직접 설계하고 구현 |
| DB | MariaDB 11.4(개발) · MySQL 8(배포) + SQLAlchemy + Alembic | PC에 설치된 MariaDB·HeidiSQL로 바로 개발, 두 DB 공통 기능만 사용 |
| 인증 | JWT 직접 구현 | 역할(환자/의사/관리자) 기반 권한 |
| 결제 | 토스페이먼츠 결제위젯 (테스트 키) | 실제와 같은 결제 → 서버 승인 흐름 |
| 지도·약국 | 카카오맵 JS SDK + 공공데이터포털 약국 정보 | 국내 지도, 백엔드에서 가공·캐싱 |
| 알림 | 1차 주기적 조회(polling), 이후 SSE | 단계적으로 실시간 구현 |
| 배포 | 프론트 Vercel, 백엔드 Render, DB Aiven MySQL (데모) | 면접관이 링크로 바로 확인 |

> 비밀 키(토스 시크릿 키, 공공데이터 인증키)는 브라우저에 노출되지 않도록 FastAPI 서버에서만 사용합니다.

## 11. 포트폴리오에서 강조할 포인트

1. **동시성 처리**: 같은 시간에 두 명이 예약해도 하나만 성공 (DB 유니크 제약 + 409 응답, 동시 요청 테스트)
2. **결제 보안**: 브라우저가 보낸 금액이 아닌 서버에 저장한 금액으로 검증, 같은 승인 요청 중복 처리 방지
3. **트랜잭션**: 진료 완료 = 상태 변경 + 처방전 저장 + 결제 요청 생성 + 알림을 하나로 처리
4. **상태 머신**: 예약·결제·약 수령 상태를 정해진 순서로만 바꾸고, 예약 상세에서 진행 단계로 표시
5. **역할 기반 권한**: 같은 앱에서 환자·의사·관리자가 보는 화면과 할 수 있는 일이 다름 (프론트 라우트 보호 + 백엔드 권한 검사, 남의 데이터는 404)
6. **의사 인증 흐름**: 면허 서류 제출 → 심사 중 → 관리자 승인, 서류는 비공개 저장
7. **제도를 반영한 설계**: 초진 처방 일수 제한, 약 배송 대상자, 알선 금지를 기능 규칙으로 반영
8. **바로 써볼 수 있는 데모**: 로그인 없이 둘러보기, README의 시연용 계정으로 환자·의사 화면 확인

## 12. 보류한 화상통화 메모

진료 단계는 지금 의사가 상태(진료 시작 / 진료 완료)만 바꾸는 방식입니다. 나중에 다시 정할 때 참고할 선택지입니다.

| 단계 | 방법 | 난이도 |
|---|---|---|
| 화면만 | 내 카메라 미리보기(브라우저 기본 기능) + 의사 쪽 가상 화면, 진료실 UI(마이크·카메라 끄기, 종료) | 쉬움 |
| 실제 연결 | 영상통화 서비스 무료 제공량 사용 (2026-04 기준 비교 자료: LiveKit 월 5,000분, Daily·Agora 월 10,000분). 환자 창·의사 창을 띄워 실제 통화 시연 | 보통 |
| 직접 구현 | WebRTC 직접 + 중계 서버 운영 | 개인 프로젝트로 비추천 |
